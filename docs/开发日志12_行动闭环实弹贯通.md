## 三、阶段1：act.py 行动闭环（五道工序）

- **决策**：告警 → 装配（官方十二字段 RectifyTask，装配即过 schema）
  → LLM 润色可选层（闸1 数字回查 + 闸2 schema 重验，双闸不过回退代码版）
  → 发送（30s 超时 + 2s/4s 指数退避；4xx 确定性不重试）
  → 微信推送（失败不否定任务）→ dispatch_log 落库 + 实时追踪聚合
- **关键裁决记录**：
  - **重试用手工循环而非 tenacity 装饰器**——backoff 可注入测试（0.01s），
    策略与 llm.py 等效；可测性优先于写法统一
  - **task_id 统一官方格式** TASK-YYYY-NNNN（废弃内部 ZG-* 格式），
    演示后缀 -FAST/-OVERDUE/-DONE 入 schema 白名单（官方状态机彩蛋的合规利用）
  - **幂等查重**：同产品同月同标题已成功发送则跳过——重复 dispatch 不产生重复任务
  - **状态真源外置**：本系统只记发送日志，追踪实时拉取 RPA，不搞双写状态
  - **责任人名册 YAML 外置**（演示数据，答辩口径：企业部署对接 HR 系统）
- **优点**：纪律条款"不过 schema 不发送"有四层实现（装配校验/润色重验/4xx 拒发/
  失败如实落库）；追踪聚合四项与官方文档 6.2 前端建议原文对齐
- **缺点**：状态真源外置 → RPA 挂了追踪页只能显示"不可达"（接受，比假数据诚实）；
  名册是演示道具（已备答辩口径）；LLM 润色层暂未实弹（模板轨已实证，
  LLM 轨待 DeepSeek 联调时顺带验证）
- **裁决**：做——模块四"不能做成摆设"的正面回答

## 六、实弹抓到的两个真问题（如实记录）

### D24. 幂等设计反噬测试【已修复】
- **现象**：API 端点测试首跑通过、二跑失败——端点走真实库，首跑落库的记录
  触发幂等跳过，二跑拿不到任务
- **决策**：端点测试前后清理本用例的 dispatch_log 记录（真实库可重复运行）；
  实弹脚本改用独立证据库 docs/e2e/rpa_live/，每次重建
- **缺点**：测试接触真实库（有清理护栏）；证据库与真实库双份（隔离是必要的）
- **教训**：幂等是生产美德、测试陷阱——凡有幂等的链路，测试必须自带清场

### D25. 数据集告警实况 vs 官方"≥3 任务"要求【如实声明，不改口径】
- **现象**：全量扫描实证——超阈值告警事件仅 2 个（银黄 5 月金银花 +12%、
  板蓝根 5 月），六味地黄胶囊全年无告警；3 月设备故障月要素环比全线负值
  （-2.9%/-4.7%/-3.9%），幅度低于 ±10% 阈值，**告警系统无漏检**
- **决策**：实弹第三场景改为验证纪律路径"无告警→不制造任务"；
  不为凑数改阈值（±10% 是赛题 5.2.3 口径）
- **缺点**：官方接口文档 5.2"至少验证 3 个整改任务"在当前数据包下只能实证 2 个——
  评测场景若含更多告警月，管线通用可触发；答辩需备口径"告警由阈值驱动，
  数据集实况如此，扫描证据可查"
- **裁决**：诚实优先于凑数——这恰是"可审计"定位的又一次自证
