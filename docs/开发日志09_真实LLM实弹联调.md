## 二、实弹抓到并修复的三个真问题

### D19. 模型返回破损 JSON → 解析层直接崩溃【已修复·双保险】

- **现象**：DeepSeek 实弹首发返回语法破损 JSON（37 行处错位），
  `json.loads` 抛 JSONDecodeError，归因生成整体崩溃——
  Mock 测试全喂合法 JSON，此坑只有实弹能暴露；
  且违反本系统自己的承诺"系统永不因模型失误而崩溃"
- **决策**：①`LLMClient.chat(json_mode=True)` 携带 `response_format: json_object`
  （OpenAI 兼容扩展，DeepSeek/Kimi/Qwen 均支持，prompt 含"JSON"字样满足前置条件）；
  ②解析失败视同 rejected 进反馈重试——板块2 两轮仍败返回 passed=False 空报告，
  板块3 两轮仍败降级模板句（`llm_parse_failed` 标注）
- **优点**：协议层把语法错误率压向零（修复后三轮实弹零复发）；
  任何模型任何输出都不再能炸穿系统
- **缺点**：`response_format` 是厂商扩展，不识别的自部署端点会 400
  （做成可关参数对冲）；两轮机会意味着出错时 token 成本翻倍
- **裁决**：做——实弹第一发就炸证明这是必然事件不是小概率

### 安全防线补强. rejected 文本曾可进入正式报告【已修复】

- **现象**（联调中代码复查发现）：`build_report` 渲染 sections 时不看 verdict——
  校验判 rejected 的 LLM 文本会原样装进 docx/PDF 交付。
  实弹恰好演了一次：板块3 首轮 rejected（"11.0" 未声明），若直接实产即带出未过校验文本
- **决策**：两轮后仍 rejected → 六段整体降级模板句（来源标注"模板句·LLM被拦截"），
  verdict 保留 rejected 如实记录 LLM 轨失败；parse 失败降级标注"模板句·LLM未配置"同轨
- **优点**：落到纸面的每一个字要么过了校验、要么出自代码模板句——
  报告文件的信任级别与 LLM 当日状态解耦；评审演示永远不会被模型抽风拖死
- **缺点**：被拦截时 LLM 文本整段弃用（token 白花）；模板句质量低于 LLM 正常发挥
  ——但"低质量的正确"优于"高质量的未验证"
- **裁决**：做——这是交付物的安全底线，不是可选项

### D20. 设备型号被数字正则捕获造成 auto_fixed 噪声【已修复】

- **现象**：板块2 首轮 auto_fixed 5 处中 4 处是 `NJP-3200`→-3200、`DXDK-40VI`→-40
  （型号中的连字符被负号规则吞掉）——数字"真实"（白名单同规则提取，两边自洽）
  但纯属噪声，污染声明清单
- **决策**：豁免域加型号模式 `[A-Za-z]{2,}-[0-9]+`；白名单与正文抽取共用
  `_numbers_in_text`，一处修改两边同步
- **优点**：修复后同类噪声归零（第二轮 auto_fixed 降至 2 处且均为真实数字）
- **缺点**：理论上存在"字母-数字"形态的真实数据被误豁免——
  成本数据域内不存在该形态的数量表达，风险可忽略
- **裁决**：做——豁免域枚举的边界纪律（D17/D18 教训）的延续
