# 开发日志23 · 收尾：chunk 拆分 + 交付清单复核

## 决策

1. **vite chunk 拆分**：`manualChunks` 函数形式按包名归组——
   `echarts`/`zrender` 进 vendor-echarts，其余 node_modules 进 vendor-vue，
   业务代码留主块。第一版用对象形式时发现 zrender 被 vue-echarts 的依赖图
   带进 vendor-vue（450KB），归属错误，改为函数形式修正。
2. **阈值校准而非隐藏**：echarts 已是按需引入（`echarts/core` + 4 图型 +
   5 组件），576KB 是热力图/可视映射等必需组件的真实体积（gzip 193KB）。
   vendor 块长期不变、浏览器长缓存一次下载终身复用，故
   `chunkSizeWarningLimit` 提至 600 豁免该已知大块；业务主块 55KB，
   将来异常膨胀仍会报警。
3. **交付清单复核**：对照 09-20 版核查清单逐项刷新——阶段3 前端缺口
   （6.10/7.9/8.7/8.9）已全部清偿，补登 8.10 知识库视图与 8.11 打包治理；
   3.5 升级为四路 RRF、6.6 升级为双向核实；五路由浏览器巡线零报错。

## 优点

- 构建输出三块职责清晰：业务 55KB / vue 80KB / echarts 576KB，并行加载
  且 vendor 缓存独立失效（改业务代码用户不用重新下载 echarts）；
- 警告消除方式是"先真实拆分、再按已知事实校准阈值"，不是掩耳盗铃；
- 核查清单与代码现状严格同步，剩余缺口全部如实标注（评测报告/演示视频
  属未到窗口，Docker 实机/小模型属环境或挂起项）。

## 缺点

1. chunkSizeWarningLimit 是全局阈值——提至 600 意味着任何块涨到 600KB
   以内都不再警告（缓解：注释写明业务块当前 55KB 的基准，膨胀十倍才会
   触线）；
2. vendor-echarts 单块 576KB 对首屏仍是最大下载项——gzip 后 193KB 可接受，
   进一步优化需按路由懒加载 echarts，但看板首页即需图表，收益小不划算；
3. 交付清单中 9.4/9.5（评测报告、演示视频）仍是 ❌——属执行窗口未到，
   不是技术缺口，但交付前必须排期。

- 浏览器巡线五路由（dashboard/benchmark/rectify/reports/kb）全部渲染、
  零 error 事件；
- 核查清单刷新版落盘（创灵境赛题_功能实现档案_人工核查清单.md），
  测试基线更新为后端 167 + 前端 69。
