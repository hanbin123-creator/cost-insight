# 开发日志 30 · Word/PDF 报告量价分解表（看板方案一延伸到交付物）

## 背景

看板归因面板已表格化（日志 27），但 Word/PDF 报告的 3.1.2 材料成本变动归因段
仍是散文——线上看板与线下交付物观感不一致。本增量把同款分解表落到报告里。

## 决策

1. **数据源**：直接复用 `metrics.decomposition`（代码同源，零新增计算）；
   在 `render_docx` 后处理阶段锚定"3.1.2 …归因"标题，把分解表插在其正文段之后。
   季度报告口径不同不插入（与 compute.quarter_pack 的"不硬凑"设计一致，有测试锁定）。
2. **正文瘦身同步**：报告 prompt 加规则 9——明细交给表，正文点头号材料讲逻辑。
3. **版式三连修**（实机 PDF 渲染逐轮比对）：
   - 整数价格保留一位小数（`130.0→138.0`，与前端 `decomp.ts` 同口径，`_fmt_pair`）
   - 固定列宽防数字串腰斩：`tblLayout=fixed` + 逐格 tcW + **tblGrid 同步**
     （LibreOffice 优先读 tblGrid，只设 tcW 不生效——实机踩坑）
   - 整表降 9pt 小五（密集数字表惯例），列宽最终 [2.2, 2.5, 3.1, 2.15, 2.15, 2.4]cm

## 优点

- 看板/Word/PDF 三端同一张表、同一组数字，答辩物料观感统一
- 表格数字代码直出，不经 LLM——报告侧的"大模型永不算数"闭环不变
- 插入机制走模板锚点查找，不动 placeholder_map.yaml/官方模板文件，模板可复用性无损

## 缺点

- 锚点依赖模板中"3.1.2 …归因"标题文本——模板若改节号/标题，表格静默不插入
  （有测试盯着：月度报告必须恰好 1 张分解表且紧跟 3.1.2 正文段，缺失即红）
- LLM 规则 9 仍是软引导，模型罗列全部数字不算违规（校验照样过）
- 列宽是按当前数据长度调的死值；材料名显著变长时 CJK 折行可接受，数字串不变

## 验证

- pytest **174 全绿**（test_report 28 项含新增：月度报告 16 表、分解表表头契约、
  六行材料齐全、符号小数位、紧跟 3.1.2 段落位置、季度报告不插入）
- 容器实机：重建 app → `/api/report` 生成（verdict pass/auto_fixed 自愈均可）→
  PDF 渲出 → pypdfium2 逐页渲染目检三轮（腰斩修复前→后对比确认）：
  最终版所有数字串单行无折断，灰底表头与模板风格一致
