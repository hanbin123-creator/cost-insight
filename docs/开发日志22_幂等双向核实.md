# 开发日志22 · 幂等双向核实（问题一修复）

> 对应演习发现的问题一：我方 dispatch_log 记"已发送"，但官方 RPA mock
> 是内存存储、重启即失忆——幂等跳过信任了"对方也记得"，演示现场出现
> "我方说发了、对方查无此单"的错位。
> 方案经 GitHub 五案例调研后定为**双向核实**：本地记录只是收据，
> 跳过前先远程核实任务仍在对方侧。

## 决策

`act.py` 幂等逻辑从"查本地库标题集合就跳过"升级为三层防线：

1. 本地 dispatch_log 有已发记录 → 逐个 `GET /api/rpa/tasks/{task_id}` 核实；
2. **200**（对方真有）→ 幂等跳过，note 如实写明"并经远程核实"；
3. **404**（对方失忆）→ 用**原 task_id** 补发（对方侧身份稳定，追踪页
   历史与补发单自然合并），结果带 `resent` 计数；
4. **网络错误**（对方不在线）→ fail-safe 不补发，响应带 `unverified: true`，
   前端整改页提示行以琥珀色警示（区别于失败的红色）——
   宁可标"待核实"也不制造重复任务；官方 mock 创建接口自带
   `task_id 已存在 → 400` 去重，是第二道保险。

配套：`_sent_titles` → `_sent_records`（带 task_id）；`RectifyDispatchResp`
加 `unverified` / `resent` 字段；RectifyView dispatch-note 增加 warn 级样式。

## 优点

- **错位根因消除**：mock 重启后下一次下发自动补发，追踪页与本方记录
  重新一致——演示现场无需任何手工干预；
- **双向防重**：我方核实 + 对方 400 去重，重复下发概率为零；
- **状态诚实**：核实通过 / 补发 / 待核实三种结局在界面上一眼可辨，
  "不把未知猜成已送达"（task-state-guard 原则）；
- 核实用对方**按单号精确查询**接口，不拉列表模糊匹配（almanak
  read-after-write 钉住确认点的思想）。

## 缺点

1. 每次重复触发多 N 次 HTTP 查询（N=已发任务数；本机环回实测每次 <5ms，
   无感；企业版任务量大时可改批量列表核实）；
2. 依赖对方提供单号查询接口——无此接口的 RPA 需退化为列表+产品月份过滤；
3. "待核实"只是提示，不含自动恢复调度——服务恢复后要等下一次手动/定时
   触发才核实补发（刻意不做后台 watcher，与 task-state-guard 的
   "reconcile 只在调用时发生"同款取舍）；
4. 补发任务的 created_at 是补发时刻而非首次发送时刻（原时间戳仍留在
   dispatch_log 首次记录里，审计可溯源）。
