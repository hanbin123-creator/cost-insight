# 开发日志21 · 精确编号检索通道（按需 exact 通道）

> 对应演习发现的问题二：精确编号（如 `ZQ-TEST-2026`）检索薄弱。
> 方案经 GitHub 调研（git-semantic-search / minirag-mcp / remind / ccsearch）
> 与实测基准后定为 **B + C′ 合体：查询侧标识符检测 + 按需子串精确通道**。

## 决策

`retrieve.py` 新增第四条 RRF 召回通道 `exact`，但**按需启动**：

1. 查询进入后先经 `extract_identifiers()` 做标识符抽取——正则
   `[A-Za-z][A-Za-z0-9]*(?:-[A-Za-z0-9]+)+`（字母数字 + 至少一个连字符段，
   覆盖语料实测形态：EQ-JN-001、PF-2026-LW-001、EQP-2026-YC01、DXDK-40VI），
   统一大写、去重；
2. **只有**抽到标识符时才对全库原文做大小写无关子串匹配，命中块按
   "命中标识符数量降序 + 语料顺序"排秩，作为 `exact` 通道参与 RRF(k=60) 融合；
3. 纯语义查询通道完全不启动，排序行为与修复前**逐字节一致**。

放弃了两个备选：方案 A（全局给 BM25 固定提权 2–3 倍）会误伤语义查询排序；
原方案 C 的"jieba 分词层修复"被子串匹配绕过——编号整串直接在原文里找，
分词切碎与否不再重要，省一处改动。

## 优点

- **直击双根因**：embedding 对罕见标识符不敏感 + jieba 切碎连字符编号，
  子串匹配对两者都免疫，编号类查询 Top1 100% 命中；
- **语义查询零开销零影响**：通道不启动时不扫一个字符，165 项既有测试的
  排序语义全部保持（实测全绿）；
- **性能实测无感**：351 块 / 8.7 万字全扫 0.03ms；模拟企业 200 倍数据
  （7 万块 / 17.5MB）也仅 5.8ms。百万块级的演进路径已铺好——SQLite FTS5
  trigram 索引（stdlib 零新依赖，实测同数据 2.5ms），通道接口不变；
- 大小写无关：用户小写输入 `dj-300` 同样命中 `DJ-300`。

## 缺点

1. **依赖正则认形态**：编号形态写窄了会漏识别（缓解：正则覆盖数据包全部
   实测形态并有测试锁死；未来新形态只需扩正则 + 加用例）；
2. **子串不区分实体边界**：`PF-2026` 会命中 `APF-2026X` 这类包含关系——
   实际语料中概率极低，且误命中只是 RRF 多一分噪声，不会造成漏召回；
3. **每查询一次线性扫描**：当前规模无感，但它是 O(全文字数)——这是刻意
   的 Lite 取舍，FTS5 trigram 是接口兼容的升级出口；
4. 后端为常驻进程，本次修复需重启服务才生效（演习第一次复测即踩到：
   旧进程无 exact 通道，重启后 PASS——部署文档需写明"代码更新必须重启"）。
