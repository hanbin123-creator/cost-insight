## 一、D11 根治：模型交付三层防线（GitHub 实例考证后定稿）

### GitHub 实例考证结论
检索 fastembed 离线/交付相关代码（102 条命中），生产项目的通行模式高度一致：
- **cuga-agent**（Dockerfile.ubi）：`FASTEMBED_CACHE_PATH=/app/.cache/fastembed` + `HF_HUB_OFFLINE=1`
- **Curator**："Bake the embedding model into the image: the container never downloads a model"
- **Citadel**：构建时跑离线冒烟断言 `RUN HF_HUB_OFFLINE=1 python -c "...embed(['smoke']); assert len(v)==384"`——**烘焙必须在构建期验证，而非生产期**
- **ai-research-assistant**：`HF_HUB_OFFLINE=1` 的注释写明动机"fails loudly on a cache-path mismatch instead of silently downloading at runtime"
- 另有中文开发者记录：**hf-mirror 在 huggingface_hub 1.x 下有元数据兼容问题**（jackluo2012/learn），印证 D11 踩的坑不是个例

### 实施（四段式）
- **决策**：三层防线——① 开发期 `scripts/download_model.py` 多源回退（HF 直连 → hf-mirror+禁xet，独立子进程保证环境变量在 huggingface_hub 导入前生效）+ 冒烟验证后才写 `.ready` 标记；② 运行期 `app/embedder.py` 工厂：缓存固定项目内 `models/fastembed/`，标记存在则 `local_files_only=True` **代码内强制离线**（不靠环境变量记忆）；③ 交付/Docker 期 COPY 缓存 + `HF_HUB_OFFLINE=1`
- **优点**：演示现场零网络依赖；模型缺失时响亮报错而非静默联网；新机器一条命令受控下载；缓存位置受控
- **缺点**：交付物 +91MB；模型升级要重跑下载脚本
- **裁决**：值得——并立即兑现了收益（见 D16）

### 连带发现
#### D16. fastembed 默认缓存落在系统 Temp 目录【已修复】
- 现象：首次下载的模型实际在 `C:\Users\...\Temp\fastembed_cache`——Windows 磁盘清理随时可能删掉，演示前一天模型消失是最典型的"昨天还能跑"事故
- 修复：本次烘焙到项目内顺带根治；已写入 `test` 之外的运行防线（.ready 标记机制）

## 二、D14 残余根治：表格感知抽取（替代碎行合并方案）

- **决策**：`_read_pdf_page` 用 `page.find_tables()` 定位表格区域，表格内按行还原并渲染为「列名: 值；…」自包含记录（单元格内换行合并），非表格区域用 `page.filter()` 排除表格后抽文本
- **优点**：根治——维修记录现在是 `日期: 2026-03；设备: 胶囊填充机NJP-3200；故障描述: 计量盘磨损导致装量偏差超标；…` 的完整行，BM25 词元完整、每行自带列名上下文（等同 Anthropic contextual retrieval 的穷人版）；所有 PDF 的配方表/设备台账同步受益（块数 437→351，更紧凑）
- **缺点**：依赖 PDF 表格有线框（本数据包有，实测检出正常；无线框表格会退回文本流——保留 `_merge_hyphen_lines` 兜底）；表格行在页文本之后进入行序列，章节归属取页内末尾章节（本库章节与表格同页相邻，可接受）
- **裁决**：值得——这是 RAG 表格处理的正道，比正则补丁高一个层级
- 验证：`test_hyphen_line_merge` 断言维修块含完整 `2026-03` 与 `NJP-3200`

## 三、D13 复核：表格感知抽取已解决，产品名加成实测后撤销

- **过程**：先实现了"查询点名产品 → 该产品文档 RRF 加成（半通道量级）"

- 教训记录：先修数据表达层（切分/抽取），再谈排序层加权；顺序反了会做多余且有害的启发式

## 四、D8 修复：SQLite 持久连接

- **决策**：`Store` 持有单连接（`check_same_thread=False`）+ 查询锁，rebuild 与查询互斥；新增 `close()`
- **优点**：FastAPI 并发场景不再每次开关连接；结构对企业版 SQLAlchemy 引擎池化是自然过渡
- **缺点**：长连接持有文件句柄（桌面 SQLite 场景无实际影响）；跨线程靠锁串行化（并发度低，竞赛规模无感）
- **裁决**：低成本消除已知瑕疵，做
